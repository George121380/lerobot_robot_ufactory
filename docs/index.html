What this repository provides

The UFACTORY package connects robot drivers, teleoperators, and cameras to LeRobot. It records demonstrations in LeRobot format and loads trained policies for real-time robot control. Policy architectures and training come from the pinned LeRobot dependency.

Your first session

Start with a short, observable task and a small dataset. Check each stage before increasing episode count, speed, or the number of arms.

  1. Identify the station.

    Confirm the xArm model, GELLO leader, gripper, cameras, controller address, and the station's stop procedure.

  2. Make a local configuration.

    Set the GELLO serial port and joint mapping, review both reference postures, add cameras, and choose a new dataset location.

  3. Test teleoperation.

    Check each leader-to-follower joint and the gripper before trying the task. This command does not test the cameras.

  4. Record a few demonstrations.

    Save intentionally; discard failed attempts while recording. Inspect the images and state/action traces.

  5. Run a small training check.

    Verify data loading and checkpoint creation. A successful training process does not establish policy quality.

  6. Evaluate under supervision.

    Use the same observation schema and camera setup. Record outcomes against a task-specific success criterion.

Startup can move the robot

connect() calls configure(), which can enable motion, open the gripper, and move to the configured start pose. A paused keyboard loop and no_action: true do not suppress these initialization movements. Check the workspace before launching any command that connects a real robot.

SET UP A STATION

Hardware & prerequisites

GELLO station hardware

  • xArm5, xArm6, or xArm7 and its controller.
  • A GELLO Dynamixel leader with the matching joint mapping, power supply, and USB-to-serial connection.
  • The configured follower gripper and GELLO gripper input.
  • Fixed camera mounts and the selected cameras for visual imitation learning.
  • A workstation with controller network access and serial-device access.

Software baseline

  • Python 3.12 for the initial environment.
  • lerobot==0.6.1, pinned by this repository.
  • The [gello] extra: GELLO software and Dynamixel SDK.
  • Ubuntu 22.04 / 24.04 are listed upstream; verify the station's actual image.
  • Camera drivers and a compatible CUDA/PyTorch setup for GPU training.

Record these details for the shared station

Keep the arm model/firmware, GELLO serial ID, ordered joint IDs and signs, torque IDs, gripper ID, reference-pose photos, camera names/mounts, software versions, and responsible maintainer in a station record. Keep the controller address and other non-public station details in the lab's normal private location.

Sources: upstream environment requirements · GELLO dependencies · GELLO configuration.

SET UP A STATION

Install the GELLO software

Use a dedicated environment on the robot workstation. Run the commands from the repository root after cloning.

git clone https://github.com/George121380/lerobot_robot_ufactory.git
cd lerobot_robot_ufactory

conda create -n uf_lerobot python=3.12 -y
conda activate uf_lerobot
python -m pip install -e ".[gello]"
python -m pip check

Find the leader's serial port

ls -l /dev/serial/by-id/
groups

Use the path belonging to the GELLO USB adapter as teleop.port. The FTDI identifier in the example YAML belongs to the upstream setup. On Ubuntu, if your user lacks access and the device belongs to dialout, add that group and log out and back in:

sudo usermod -aG dialout "$USER"

Power the leader and ensure no other process is using its serial port. The adapter communicates at 57600 baud in this integration. The GELLO extra depends on Git repositories without fixed commit pins; record the resolved versions in the tested station environment.

Check package versions and cameras

python -c "import importlib.metadata as m; print('LeRobot:', m.version('lerobot')); print('UFACTORY:', m.version('lerobot_robot_ufactory'))"
uf-camera-view -l

Expected: LeRobot reports 0.6.1 and the UFACTORY package reports 0.2.0. Verify fresh images with the appropriate camera viewer and install the selected camera's driver/backend before recording. Listing devices alone does not validate their images.

References: upstream GELLO setup · serial initialization.

SET UP A STATION

Configure your GELLO station

Copy the example for the actual follower arm. Set XARM_MODEL to 5, 6, or 7; the value 6 below is only an example.

export XARM_MODEL=6
mkdir -p config/local
cp "config/gello/xarm${XARM_MODEL}_gello_record_config.yaml" config/local/lab_gello.yaml
export LAB_CONFIG="$PWD/config/local/lab_gello.yaml"

config/local/ is ignored by Git. Edit $LAB_CONFIG before launching a robot command, and keep the original example available for comparison.

Add cameras before collecting a visual-policy dataset

Merge this illustrative OpenCV block into the existing robot: section. Replace the device path and use resolution/FPS values supported by your camera. Do not create a second robot: key.

  cameras:
    front:
      type: opencv
      index_or_path: "/dev/v4l/by-id/REPLACE_WITH_CAMERA_ID"
      width: 640
      height: 480
      fps: 30

front is an example camera name. Keep your chosen names, mounts, and image sizes consistent across collection, training, and rollout. A RealSense backend requires its own configuration and dependencies; use the station's tested camera setup. A successful camera-free teleoperation test does not validate a visual dataset.

SET UP A STATION

Check GELLO alignment

GELLO maps leader motor readings to absolute follower joint targets. Alignment is established when the Python object is constructed, before the interactive loop begins.

  1. Review the mapping.

    Check the ordered joint_ids, joint_signs, both start_joints arrays, gripper ID, and torque IDs against the station record.

  2. Place the leader in its reference posture before launching.

    The constructor reads the current leader angles and calculates offsets against teleop.start_joints. Hold the intended open reference on the GELLO gripper input while those readings are taken.

  3. Check one follower joint at a time.

    After the configured startup motion, use small leader movements to confirm the corresponding follower joint, direction, and range. Return the leader to the matching reference before starting the next check.

  4. Verify the gripper across its usable travel.

    Confirm that the open reference produces open, squeezing closes the follower gripper, and the output does not immediately saturate. Record the verified reference in the station instructions.

Space and episode reset do not recalibrate GELLO

calibrate() and configure() are no-ops, and GELLO inherits a no-op set_teleop_enabled(). The offsets stay fixed for that process. A pause lets you reposition the leader, but resuming sends its current absolute target. Return it to a posture matching the follower before resuming; for a new reference, stop and relaunch from the reviewed posture.

Understand the gripper reference

The adapter uses the initial gripper motor angle minus 0.2° as the open endpoint and minus 42° as the closed endpoint. These are fixed offsets in code, not a guided calibration routine. Check that this travel and direction match the leader on the bench.

Keep camera geometry consistent

Keep camera mounts, names, field of view, and preprocessing consistent through collection and deployment. GELLO joint mapping does not require Vive/SLAM tracking or a tracker-to-robot transform.

References: startup offsets and gripper endpoints · no-op calibration/configuration · base enable hook · GELLO dependency normalization.

EXPERIMENT / 01

Teleoperate before recording

Place the GELLO leader and gripper input in their reviewed reference postures before launching. Check the configured startup motion, then test the joint mapping with small movements.

uf-robot-teleop --config_path "$LAB_CONFIG" --fps 30
KeyTeleoperation behavior
SpaceStart or pause teleoperation.
←Request reset and pause. Resuming can move the follower to its start pose; GELLO offsets remain unchanged.
EnterShow the current keyboard help.
EscExit the loop and disconnect.

Check: each GELLO joint maps to the intended follower joint, the reference posture is correct, and the gripper direction is correct. Resolve jumps, unexpected motion, or error codes before collecting demonstrations.

The teleoperation entry point removes cameras from the configuration. Check camera feeds separately with uf-camera-view, then verify the actual recording output. Keep an interactive terminal focused when using the terminal keyboard fallback.

A software pause is not a hardware emergency stop

The keyboard loop can stop issuing new commands, but an already issued motion can still be in progress. Know the station's physical emergency-stop procedure before operating the robot.

Reference: teleoperation entry point.

EXPERIMENT / 02

Record demonstrations

Choose a fresh dataset root for a new collection. The following is a short validation session, not a recommended training-set size.

uf-lerobot-record \
  --config_path "$LAB_CONFIG" \
  --dataset.num_episodes=3 \
  --dataset.episode_time_s=30 \
  --dataset.push_to_hub=false
KeyRecording behavior
SpaceStart an episode and reconfigure the follower to its start pose. GELLO offsets are not re-established; return the leader to the matching reference first.
→End and save the current episode. Reaching the time limit also leads to saving.
←Discard the current episode buffer and prepare to re-record.
EscExit. Save an episode explicitly before exiting if you want to retain it.
EnterShow controls for the current state.

Reset the objects and return GELLO to its reference posture between episodes. The recorder moves the follower to its configured start pose when each episode begins. Record the intended task consistently. reset_time_s appears in examples, but the custom recording loop does not use it to enforce an automatic reset interval.

Continue an existing collection

uf-lerobot-record --config_path "$LAB_CONFIG" --resume true

Use the same dataset root, ID, FPS, feature names, and camera setup. The resume path checks compatibility. Do not treat a changed camera mount or action convention as the same dataset merely because the tensor shapes match.

What gets saved

Each frame contains the measured follower joint state, GELLO joint/gripper targets, configured camera images, and task (after the configured processing). Numeric observations/actions and episode metadata are managed by LeRobot; camera streams are stored according to its dataset/video configuration. streaming_encoding can reduce the work left at episode save time, but it does not establish hardware synchronization.

References: recording lifecycle · per-frame data flow.

EXPERIMENT / 03

Inspect before scaling up

Set these values to the dataset actually saved by the recorder. They are examples to replace, not paths that already exist on the workstation.

export DATASET_ROOT="/absolute/path/to/your/recorded_dataset"
export DATASET_ID="your_namespace/your_dataset"

lerobot-dataset-viz \
  --root="$DATASET_ROOT" \
  --repo-id "$DATASET_ID" \
  --episode-index 0 \
  --display-compressed-images true
  • Every expected camera is present, correctly oriented, and updating.
  • Objects and the gripper stay in view throughout the task.
  • State/action curves have plausible units and no unexplained discontinuities.
  • Gripper open/close values agree with the images.
  • Episode starts, endings, and the task description are correct.
  • The record loop is not repeatedly reporting a rate below the requested FPS.

Keep a collection log with the code revision, configuration, environment versions, camera-mount reference, operator, task, and rejected episodes. When editing or merging datasets, write a new derived dataset so the original collection remains available.

Reference: upstream dataset tools. Use lerobot-edit-dataset --help for the installed version's operation arguments.

EXPERIMENT / 04

Train a first policy

Training is provided by LeRobot. This ACT example is a short pipeline check using the GELLO joint-action dataset selected above. Configure and verify the intended camera observations before using this visual-policy example. The step count and batch size are starting values for debugging, not a claim about task performance.

export RUN_DIR="$PWD/outputs/act_smoke_$(date +%Y%m%d_%H%M%S)"

lerobot-train \
  --dataset.root="$DATASET_ROOT" \
  --dataset.repo_id="$DATASET_ID" \
  --policy.type=act \
  --policy.device=cuda \
  --policy.push_to_hub=false \
  --output_dir="$RUN_DIR" \
  --job_name=act_smoke \
  --steps=2000 \
  --batch_size=8 \
  --save_freq=1000 \
  --wandb.enable=false

Expected: the dataset loads with the intended image and state features, the training loss is finite, and a checkpoint is saved. Inspect the generated training configuration and the actual selected device.

Keep train/validation splits at the episode level. For a task evaluation, also hold out relevant objects, arrangements, or conditions rather than relying on neighboring video frames as independent test samples. Choose the final training schedule after checking data quality and task performance.

To explore Diffusion Policy or another supported model, follow the pinned LeRobot version's configuration. Robot-side state/action meanings, FPS, and preprocessing must still match the demonstrations.

References: upstream ACT training example · LeRobot 0.6.1.

EXPERIMENT / 05

Run the trained policy

Use a checkpoint trained on this station's GELLO joint-action dataset and its metadata/statistics. Keep robot.control_space: joint, joint order, gripper convention, camera setup, start posture, and FPS consistent. During rollout the policy supplies actions; GELLO is not an intervention controller in this evaluation loop.

export POLICY_PATH="$RUN_DIR/checkpoints/last/pretrained_model"

uf-lerobot-eval \
  --config_path "$LAB_CONFIG" \
  --dataset.root="$DATASET_ROOT" \
  --dataset.repo_id="$DATASET_ID" \
  --policy.path "$POLICY_PATH"
KeyRollout behavior
SpaceStart, pause, or resume policy execution.
←Stop the current episode and request reset. Starting again reconfigures the robot and resets policy/processor state.
EscExit and disconnect.
EnterShow the current controls.
Preserve the GELLO joint-action schema

Use absolute joint targets with the default relative=False. The evaluation script's relative-pose option operates on Cartesian pose fields; it does not turn this checkpoint into a relative-joint policy. Keep collection and rollout in joint space.

uf-lerobot-eval is an interactive deployment loop. It does not provide automated success-rate measurement, and n_episodes is not consumed to bound the loop. Log trials separately: checkpoint, initial condition, success/failure, intervention, and failure mode. Define task success before comparing policies.

End the session

Exit the running process and verify that the arm has stopped. Follow the station's normal parking and power-down procedure. Save the session's configuration and outcome log with the dataset or checkpoint record.

Reference: policy rollout implementation.

REFERENCE

State & action conventions

For the default single-arm GELLO setup with a gripper, the state contains the follower's n joint angles and gripper position. Actions contain n absolute joint targets and one gripper target: 6, 7, or 8 values for xArm5, xArm6, or xArm7 respectively. Configured camera images are additional observations.

FieldMeaningUnit / convention
J1.pos … Jn.pos in observationsMeasured follower joint positionsRadians, in follower joint order
J1.pos … Jn.pos in actionsMapped GELLO targets during collection; policy targets during rolloutAbsolute radians, not per-step deltas
gripper.posNormalized gripper state / target0 = open, 1 = closed for the standard mapping; check both ends on the station
robot.start_jointsFollower initialization/home postureDegrees in YAML
teleop.start_jointsTarget values assigned to the leader's startup postureDegrees in YAML; converted to radians for offset calculation
joint_ids, joint_signsOrdered leader-to-follower motor mappingOne motor ID and sign per arm joint; the gripper ID is separate
J1.vel … Jn.velOptional measured joint velocitiesOnly when observe_joint_vel is enabled; changes the observation schema
Camera keys, e.g. frontImages from robot.camerasPreserve names, image shapes, and preprocessing

The saved action is the teleoperator-processor output. If a custom robot-action processor clips or transforms it, the label can differ from the executed command. Inspect both joint state and action traces before scaling up a collection.

References: GELLO action fields · follower observations and commands · action-processing boundary.

Troubleshooting

Start with the smallest failing component. Preserve the error message and station configuration before changing several settings at once.

SymptomFirst checks
GELLO serial permission / port errorThe actual /dev/serial/by-id/ path, USB connection, device ownership/group membership after login, and whether another process has the port open.
Dynamixel reads fail or startup stallsLeader power, motor IDs, serial adapter, and 57600-baud communication. The constructor reads motors before the control loop is ready.
Wrong joint moves or moves backwardsOrdered joint_ids, joint_signs, actual xArm model, and equal-length mapping/reference arrays.
Jump at startup, resume, or the next episodeThe leader's posture when the process started, both start_joints arrays, and whether the leader was returned to match the follower. Space/reset does not recompute offsets.
Gripper inverted or saturates immediatelyGripper motor ID, open posture at startup, and the adapter's fixed −0.2° / −42° endpoints. Verify follower gripper_type.
Robot connection or DOF errorController address, host network, controller status, and configured 5/6/7 DOF.
Teleoperation works but the dataset has no imagesAdd robot.cameras; all upstream GELLO examples omit it. The teleoperation command deliberately removes cameras.
Camera missing, frozen, or recording slowCamera path/backend, driver/permissions, supported mode, competing applications, USB bandwidth, encoding load, and disk throughput.
Dataset already existsUse --resume true only for the same collection, or choose a new root and ID. Replace the example dataset paths before the first run.
Keyboard controls do not respondUse an interactive terminal and keep it focused for the terminal fallback.
Policy feature mismatchArm DOF, joint/gripper features, optional velocities, camera keys and shapes, dataset metadata, and checkpoint preprocessing. Keep control_space: joint.

References: GELLO adapter · keyboard backends · camera-free teleoperation test.

Known implementation limits

These notes apply to the reviewed upstream snapshot 5fe6fb1.

GELLO offsets are captured only at startup

The constructor computes joint offsets and fixed gripper endpoints from the current leader readings. The calibration/configuration hooks do not recompute them, and the episode enable hook is a no-op. Repeat the reference-posture check on every process launch and align the leader before resuming.

GELLO source →
The no-gripper configuration needs code review

Although the config comments describe gripper_id: -1, action_features always declares gripper.pos and get_action() always reads an extra element after the arm joints. Do not assume removing the gripper works with this adapter unchanged.

Action construction →
Mock recording is not physical simulation

UFMockRobot takes its state from the active teleoperator and returns actions without physical execution. The state_offset_action delay code is commented out. It does not model dynamics, contact, or robot latency.

UFMockTeleop is a different class: it connects to a real arm for programmatic motion/data generation. Do not infer “no hardware motion” from the word Mock alone.

Mock robot source →
Timing and joint-target transitions need validation

The rollout smoothing branch is Cartesian-only and disabled by default; it does not smooth GELLO joint targets. Gripper look-ahead application code is commented out. The recorder reads state and cameras sequentially and uses timing sleeps; a configured 30 FPS does not establish synchronized camera/robot measurements or a sustained 30 Hz loop.

Rollout settings →
Version and configuration maintenance

The package requires Python ≥3.12, despite the older ≥3.10 statement in the Chinese README. LeRobot is pinned to 0.6.1, while several peripheral dependencies are not pinned to commits. The custom parser can remove unknown configuration fields, so a typo may not always be rejected. Review the logged effective configuration.

The reviewed upstream tree contains no test files or CI workflows. Hardware compatibility remains a station-specific validation task.

OPTIONAL REFERENCE

Other devices

The lab's primary workflow is GELLO. For occasional use of another input device, start from its upstream configuration and review that path separately.

Pika, UMI, and SpaceMouse entry points
  • Pika example: Cartesian tracking with Vive.
  • UMI example: Cartesian tracking with SLAM or Vive; the bundled XVLib libraries target Linux x86-64.
  • SpaceMouse example: current implementation only supplies XY movement and a fixed gripper output. Its delta integration is present in recording, not the generic teleoperation test.

Tracker transforms, Cartesian rotation-vector actions, and device-specific SDKs belong to those workflows. They are not part of the GELLO setup above.

Cartesian relative-pose rotation continuity Reproduced

continuous_rotvec() considers both +θ and −θ on the same axis as equivalent. They generally represent different rotations. Calling the original function with new=[0,0,1] and previous=[0,0,-0.9] returns [0,0,-1], changing the target rotation by 2 radians.

This issue does not affect the default GELLO joint-action path. The helper is used in to_absolute_pose() and the relative rollout path. Resolve this before using that path. Default rollout has relative=False.
