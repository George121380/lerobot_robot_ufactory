What this repository provides

The UFACTORY package connects robot drivers, teleoperators, and cameras to LeRobot. It records demonstrations in LeRobot format and loads trained policies for real-time robot control. Policy architectures and training come from the pinned LeRobot dependency.

START HERE

Your first session

Start with a short, observable task and a small dataset. Check each stage before increasing episode count, speed, or the number of arms.

  1. Identify the station.

    Confirm the robot model, gripper, input device, cameras, controller address, and the station's stop procedure.

  2. Make a local configuration.

    Replace device identifiers, review home poses and coordinate transforms, and choose a new dataset location.

  3. Test teleoperation.

    Check each motion axis and the gripper before trying the task. This command does not test the cameras.

  4. Record a few demonstrations.

    Save intentionally; discard failed attempts while recording. Inspect the images and state/action traces.

  5. Run a small training check.

    Verify data loading and checkpoint creation. A successful training process does not establish policy quality.

  6. Evaluate under supervision.

    Use the same observation schema and camera setup. Record outcomes against a task-specific success criterion.

Startup can move the robot

connect() calls configure(), which can enable motion, open the gripper, and move to the configured start pose. A paused keyboard loop and no_action: true do not suppress these initialization movements. Check the workspace before launching any command that connects a real robot.

SET UP A STATION

Hardware & prerequisites

Station hardware

  • xArm5, xArm6, or xArm7 and its controller.
  • The gripper selected by gripper_type.
  • One supported teleoperation device.
  • Stable camera mounts and the configured cameras.
  • A host with controller network access and the required USB/serial connections.

Software baseline

  • Python 3.12 or newer; use 3.12 for the initial environment.
  • lerobot==0.6.1, as pinned by this repository.
  • Ubuntu 22.04 / 24.04 are listed in the upstream README.
  • A compatible CUDA/PyTorch setup for GPU training.
  • Device-specific SDKs and Linux permissions.
UMI has an additional platform constraint

The bundled XVLib libraries are Linux x86-64 binaries. Upstream's XVSDK installation instructions name an Ubuntu Focal package, while its general requirements list newer Ubuntu versions. Confirm a working SDK/OS combination before adopting a station image; macOS or ARM compatibility is not established by this repository.

Record these details for every shared station

Keep a station record with the arm model and firmware, gripper, controller address, camera names and mounting photos, teleoperator IDs, SDK versions, reference poses, and responsible maintainer. Store non-public station details in the lab's normal private location. The public guide contains no lab-specific network settings.

Sources: upstream environment requirements · Python and package constraints · robot configuration fields.

SET UP A STATION

Install the software

Use a dedicated environment on the robot workstation. The commands below install the fork and its Python dependencies; peripheral SDK setup is a separate step.

git clone https://github.com/George121380/lerobot_robot_ufactory.git
cd lerobot_robot_ufactory

conda create -n uf_lerobot python=3.12 -y
conda activate uf_lerobot
python -m pip install -e .
python -m pip check

SET UP A STATION

Configure your station

Copy the closest example. Keep the upstream examples intact so it is easy to compare local changes after an update.

mkdir -p config/local
cp config/umi/xarm6_umi_record_config.yaml config/local/lab_xarm6_umi.yaml
export LAB_CONFIG="$PWD/config/local/lab_xarm6_umi.yaml"

config/local/ is ignored by Git in this fork. Edit $LAB_CONFIG before launching a robot command. If the station uses a different arm or teleoperator, copy the matching example instead.

Configuration fieldWhat to set and verify
robot.type, robot_dofSelect the physical or Mock implementation and the real arm's 5/6/7 degrees of freedom. A real robot connection checks the DOF.
robot_ip, gripper_typeUse the station's controller and actual gripper. Check the enum in UFRobot.
control_spacejoint for the GELLO examples; cartesian for the Pika/UMI examples. Keep it consistent through collection, training, and rollout.
start_joints, start_tcp_poseUse station-reviewed start poses. Joint angles and TCP RPY angles in these configuration fields are in degrees.
max_joint_velocity, max_linear_velocityReview limits for the task and hardware. These fields are expressed in degrees/s and mm/s respectively; initialization has separate motion calls.
robot.camerasReplace serial numbers or device paths. Verify each camera name, resolution, FPS, pixel format, and mount. Some examples, including xArm6 GELLO, do not configure cameras.
teleopSet the device ID or serial port, tracking mode, gripper use, and frame mapping. GELLO also needs correct joint IDs and signs.
dataset.root, repo_idChoose a new writable local dataset directory and a stable namespace/dataset_name. Avoid names beginning with eval_ for collection.
single_task, fpsWrite an unambiguous task description. Choose a rate the entire camera/robot/write loop can sustain.
num_episodes, episode_time_sUse a small collection for the first validation; episode time is a maximum recording duration.
push_to_hubKeep false for a local collection. Upload only through the lab's established dataset-sharing process.

Relative paths are interpreted from the working directory. Prefer absolute dataset paths and keep all workflow commands in the repository root. Use the dataset ID and root reported by the recorder for later training and visualization.

Check frames & calibration

Three distinct checks matter: tracking calibration, teleoperator-to-robot mapping, and the camera arrangement used for learning. The presence of a calibrate() method does not mean all three happen automatically; several implementations are no-ops.

GELLO reference posture

The constructor reads the leader joints and derives offsets relative to start_joints and joint_signs. Put the leader in the intended reference posture before initialization and verify each joint mapping with the station owner.

Pika and UMI frame mapping

tracker_to_robot_eef and robot_base_pose establish the mapping. Pika/UMI then use movement relative to the initial tracker pose to produce an absolute target in the robot frame. Check small translations along each axis and small rotations before attempting a task.

Vive and SLAM

For Vive-based setups, follow the upstream tracking calibration procedure after changing the base-station layout. uf-vive-calibrate forces calibration and deletes the existing ~/.config/libsurvive/config.json before starting; preserve the station's known-good calibration before using it. UMI SLAM mode waits for sufficient confidence at startup and holds the last action on low-confidence readings.

Camera consistency

Keep camera mounting, field of view, image names, and preprocessing consistent between collection and deployment. Moving cameras changes the policy's observation distribution. This package does not provide Raiden's automated hand-eye calibration workflow.

References: GELLO offsets · UMI mapping · Vive calibration script.

EXPERIMENT / 01

Teleoperate before recording

After checking startup motion and the configured poses, test the selected input device with the robot. The example below is for the UMI walkthrough.

uf-robot-teleop --config_path "$LAB_CONFIG" --fps 30
KeyTeleoperation behavior
SpaceStart or pause teleoperation.
←Request reset and pause. Resuming can call robot.configure() and move to the start pose.
EnterShow the current keyboard help.
EscExit the loop and disconnect.

Check: input motion maps to the intended robot axis, the reference pose is correct, and the gripper direction is correct. Resolve jumps, unexpected motion, or error codes before collecting demonstrations.

The teleoperation entry point removes cameras from the configuration. Check camera feeds separately with uf-camera-view, then verify the actual recording output. Keep an interactive terminal focused when using the terminal keyboard fallback.

A software pause is not a hardware emergency stop

The keyboard loop can stop issuing new commands, but an already issued motion can still be in progress. Know the station's physical emergency-stop procedure before operating the robot.

Reference: teleoperation entry point.

EXPERIMENT / 02

Record demonstrations

Choose a fresh dataset root for a new collection. The following is a short validation session, not a recommended training-set size.

uf-lerobot-record \
  --config_path "$LAB_CONFIG" \
  --dataset.num_episodes=3 \
  --dataset.episode_time_s=30 \
  --dataset.push_to_hub=false
KeyRecording behavior
SpaceStart an episode. For UFACTORY base teleoperators, the robot is configured and the teleop reference is re-established.
→End and save the current episode. Reaching the time limit also leads to saving.
←Discard the current episode buffer and prepare to re-record.
EscExit. Save an episode explicitly before exiting if you want to retain it.
EnterShow controls for the current state.

Reset the objects between episodes and record the intended task consistently. reset_time_s appears in examples, but the custom recording loop does not use it to enforce an automatic reset interval.

Continue an existing collection

uf-lerobot-record --config_path "$LAB_CONFIG" --resume true

Use the same dataset root, ID, FPS, feature names, and camera setup. The resume path checks compatibility. Do not treat a changed camera mount or action convention as the same dataset merely because the tensor shapes match.

What gets saved

Each frame contains the processed robot observation, teleoperator action, and task. Numeric observations/actions and episode metadata are managed by LeRobot; camera streams are stored according to its dataset/video configuration. streaming_encoding can reduce the work left at episode save time, but it does not establish hardware synchronization.

References: recording lifecycle · per-frame data flow.

EXPERIMENT / 03

Inspect before scaling up

Set these values to the dataset actually saved by the recorder. They are examples to replace, not paths that already exist on the workstation.

export DATASET_ROOT="/absolute/path/to/your/recorded_dataset"
export DATASET_ID="your_namespace/your_dataset"

lerobot-dataset-viz \
  --root="$DATASET_ROOT" \
  --repo-id "$DATASET_ID" \
  --episode-index 0 \
  --display-compressed-images true
  • Every expected camera is present, correctly oriented, and updating.
  • Objects and the gripper stay in view throughout the task.
  • State/action curves have plausible units and no unexplained discontinuities.
  • Gripper open/close values agree with the images.
  • Episode starts, endings, and the task description are correct.
  • The record loop is not repeatedly reporting a rate below the requested FPS.

Keep a collection log with the code revision, configuration, environment versions, camera-mount reference, operator, task, and rejected episodes. When editing or merging datasets, write a new derived dataset so the original collection remains available.

Reference: upstream dataset tools. Use lerobot-edit-dataset --help for the installed version's operation arguments.

EXPERIMENT / 04

Train a first policy

Training is provided by LeRobot. This ACT example is a short pipeline check using the dataset selected above. The step count and batch size are starting values for debugging, not a claim about task performance.

export RUN_DIR="$PWD/outputs/act_smoke_$(date +%Y%m%d_%H%M%S)"

lerobot-train \
  --dataset.root="$DATASET_ROOT" \
  --dataset.repo_id="$DATASET_ID" \
  --policy.type=act \
  --policy.device=cuda \
  --policy.push_to_hub=false \
  --output_dir="$RUN_DIR" \
  --job_name=act_smoke \
  --steps=2000 \
  --batch_size=8 \
  --save_freq=1000 \
  --wandb.enable=false

Expected: the dataset loads with the intended image and state features, the training loss is finite, and a checkpoint is saved. Inspect the generated training configuration and the actual selected device.

Keep train/validation splits at the episode level. For a task evaluation, also hold out relevant objects, arrangements, or conditions rather than relying on neighboring video frames as independent test samples. Choose the final training schedule after checking data quality and task performance.

To explore Diffusion Policy or another supported model, follow the pinned LeRobot version's configuration. Robot-side state/action meanings, FPS, and preprocessing must still match the demonstrations.

References: upstream ACT training example · LeRobot 0.6.1.

EXPERIMENT / 05

Run the trained policy

Use a reviewed checkpoint and the corresponding dataset metadata/statistics. Confirm camera names, image preprocessing, action representation, start pose, and dataset FPS before connecting the robot.

export POLICY_PATH="$RUN_DIR/checkpoints/last/pretrained_model"

uf-lerobot-eval \
  --config_path "$LAB_CONFIG" \
  --dataset.root="$DATASET_ROOT" \
  --dataset.repo_id="$DATASET_ID" \
  --policy.path "$POLICY_PATH"
KeyRollout behavior
SpaceStart, pause, or resume policy execution.
←Stop the current episode and request reset. Starting again reconfigures the robot and resets policy/processor state.
EscExit and disconnect.
EnterShow the current controls.
Keep the first rollout on the default absolute-action path

Do not add --relative to an absolute-action checkpoint. It changes observation/action semantics, and the current relative-pose helper has a reproduced rotation-equivalence bug. See known implementation limits.

uf-lerobot-eval is an interactive deployment loop. It does not provide automated success-rate measurement, and n_episodes is not consumed to bound the loop. Log trials separately: checkpoint, initial condition, success/failure, intervention, and failure mode. Define task success before comparing policies.

End the session

Exit the running process and verify that the arm has stopped. Follow the station's normal parking and power-down procedure. Save the session's configuration and outcome log with the dataset or checkpoint record.

Reference: policy rollout implementation.

State & action conventions

A typical single-arm Cartesian configuration has six pose values and one gripper value, plus camera images in the observation. Optional joint-velocity features and multi-arm configurations change the schema.

FieldMeaningUnit or convention
J1.pos … Jn.posJoint state / targetRadians internally
pose.x / y / zEnd-effector position / targetMillimeters
pose.rx / ry / rzRotation vector (axis × angle)Radians; not Euler RPY
gripper.posNormalized gripper positionUsually 0 = open, 1 = closed; mapped to device units
start_jointsConfiguration start postureDegrees, converted internally
start_tcp_poseConfiguration start poseXYZ in mm, then roll/pitch/yaw in degrees
left.* / right.*Multi-arm fieldsEach child arm's own frame; the prefix is not a shared world-frame transform

Pika and UMI use relative input-device movement to generate absolute robot targets. That is distinct from training a policy to predict relative actions. In the record loop, the saved action is the teleoperator-processor output; if a custom robot-action processor clips or transforms it, the saved label can differ from the executed command.

References: observation/action implementation · multiple-arm wrapper · action-processing boundary.

Troubleshooting

Start with the smallest failing component. Preserve the error message and station configuration before changing several settings at once.

SymptomFirst checks
Robot connection or DOF errorController address, host network, controller status, and configured 5/6/7 DOF.
RT Report … NOT READYThe Cartesian observation path uses controller port 30000. Check reachability, firmware/report compatibility, and any preceding thread exception.
Camera missing or frozenUSB/device permissions, serial/path, requested mode, competing applications, and fresh frames. A cached last frame can conceal camera-read failures.
UMI cannot load a shared libraryLinux x86-64 platform, the installed XVSDK, native dependencies, and the station's tested OS image.
UMI SLAM never becomes readyTracking visibility, scene texture/lighting, device connection, and confidence output. Resolve tracking before robot motion.
Wrong direction or large first movementStart posture, joint signs/offsets, frame mapping, and the distinction between Euler configuration angles and rotation-vector actions.
Recording slower than requested FPSCamera rate/resolution, image encoding, disk throughput, and CPU load. Reduce one load source and measure again.
Dataset already existsUse --resume true only for the same collection, or choose a new root and ID.
Keyboard controls do not respondUse an interactive terminal and keep it focused for the terminal fallback. Do not launch first rollouts through a detached non-interactive process.
Policy input shape or feature mismatchDataset metadata, camera keys, image size, control space, gripper fields, and checkpoint preprocessing.

References: real-time report reader · keyboard backends · UMI camera caching.

Known implementation limits

These notes apply to upstream 5fe6fb1. This documentation change does not modify the robot-control code.

Relative-pose rotation continuity Reproduced

continuous_rotvec() considers both +θ and −θ on the same axis as equivalent. They generally represent different rotations. Calling the original function with new=[0,0,1] and previous=[0,0,-0.9] returns [0,0,-1], changing the target rotation by 2 radians.

The helper is used in to_absolute_pose() and the relative rollout path. Resolve this before using that path. Default rollout has relative=False.

Source →
Mock recording is not physical simulation

UFMockRobot takes its state from the active teleoperator and returns actions without physical execution. The state_offset_action delay code is commented out. It does not model dynamics, contact, or robot latency.

UFMockTeleop is a different class: it connects to a real arm for programmatic motion/data generation. Do not infer “no hardware motion” from the word Mock alone.

Mock robot source →
SpaceMouse is a limited demonstration path

The current output only moves in XY: Z is forced to zero, rotation control is commented out, and gripper output is fixed. The recording loop integrates its position deltas; the generic teleoperation test loop does not contain that conversion. Review this path before using it as a general end-effector controller.

SpaceMouse source →
Smoothing and synchronization are not guaranteed

SMOOTH_THRESHOLD=0 disables the rollout smoothing branch by default. Gripper look-ahead application code is commented out. The recorder reads state and cameras sequentially and uses timing sleeps; a configured 60 FPS does not establish synchronized camera/robot measurements or a sustained 60 Hz loop.

Version and configuration maintenance

The package requires Python ≥3.12, despite the older ≥3.10 statement in the Chinese README. LeRobot is pinned to 0.6.1, while several peripheral dependencies are not pinned to commits. The custom parser can remove unknown configuration fields, so a typo may not always be rejected. Review the logged effective configuration.

The reviewed upstream tree contains no test files or CI workflows. Hardware compatibility remains a station-specific validation task.
